## 🇺🇸 English

### Overview

The Privacy Gateway (PG) is the **enforcement** component of the LGPD compliance framework. It acts as a privacy firewall, positioned between IoT devices and the backend services of the ecosystem.

Its primary responsibility is to intercept 100% of raw telemetry generated by devices and apply privacy and consent policies in real-time, before any data is forwarded to any other service.

The PG is designed to be:

- **Reactive:** Responds instantly to consent changes (revocations, grants) published by the Consent Management Module (CMM).
- **Performant:** Uses a high-speed in-memory cache (Redis) to make privacy enforcement decisions with near-zero latency, without querying the CMM on every incoming data packet.
- **Stateful:** Capable of executing complex, temporal privacy strategies, such as data aggregation (e.g., "transmit only the 60-second average").
- **Extensible:** Built on the *Strategy Pattern*, allowing new data treatment algorithms (anonymization, obfuscation, etc.) to be added without modifying the core gateway logic.

---

### Architecture and Technologies

The PG is an independent Python service, built with a focus on resilience and asynchronous processing.

| Component | Technology | Role |
|---|---|---|
| Language | **Python 3.12** | — |
| Messaging (Core) | **Paho-MQTT** | Receive raw telemetry, receive CMM cache invalidation notifications, publish processed data |
| Cache & State | **Redis** | Cache active privacy policies, accumulate data for temporal strategies, manage the scheduler task queue (Sorted Sets) |
| HTTP Client | **Requests** | Communicate with the CMM REST API on a cache miss |
| Parallelism | **Threading** | Run the MQTT ingestion loop and the temporal Scheduler loop concurrently |

### Design Patterns and Core Logic

The PG's functionality is based on three main design patterns working in concert.

#### a. Strategy Pattern

This is the backbone of the data treatment logic. Instead of a monolithic `if/elif/else` block in the gateway, the *how* of each treatment is delegated to specific strategy classes.

1. **Base Interface (`TreatmentStrategy`):** Defines a common contract with an `execute()` method.
2. **Accumulation Interface (`AccumulatedStrategy`):** A specialization that inherits from the base and adds a `calculate_aggregated_data()` contract, separating ingestion logic from computation logic.
3. **Concrete Strategies (`RawStrategy`, `AverageStrategy`):**
   - `RawStrategy.execute()`: Returns the original payload unchanged.
   - `AverageStrategy.execute()`: Adds the data point to Redis and returns `None`.
   - `AverageStrategy.calculate_aggregated_data()`: Receives a list of data from Redis and returns the arithmetic mean.
4. **Factory (`treatments.factory`):** The `Scheduler` and `Gateway` use the factory (`get_treatment_strategy()`) to get the correct strategy instance based on the `policy_key`, without ever knowing the implementation details.

This design strictly adheres to the **Open/Closed Principle (OCP)**: new privacy algorithms (e.g., K-Anonymity, Partial Masking) can be added by creating a single new class file, with **zero modifications** to the core gateway orchestrator.

#### b. State Management with Redis (`CacheManager`)

The `core/cache_manager.py` is the sole module responsible for all Redis communication. It manages three distinct types of data:

| Data Type | Redis Key | Redis Type | Logic |
|---|---|---|---|
| **Policy Cache** | `policy:{subject_id}:{device_id}` | `String` (JSON) | Stored with `SETEX` (auto-TTL); invalidated by CMM push notifications |
| **Accumulated Data** | `data:{subject_id}:{device_id}` | `List` | `AverageStrategy` uses `LPUSH` to add points; `Scheduler` uses `LRANGE` + `DEL` to consume atomically |
| **Task Queue** | `tasks:aggregation_due` | `Sorted Set` | `Scheduler` adds tasks with `ZADD` using execution `timestamp` as score; consumes with `ZRANGEBYSCORE(0, now)` |

#### c. Asynchronous Processing (Scheduler)

The PG runs on two main threads to prevent blocking:

1. **Main Thread (Data Ingestion):** `mqtt_client.loop_forever()` runs in the foreground. Its sole function is to receive messages as fast as possible and delegate them.
2. **Scheduler Thread (Temporal Processing):** The `Scheduler` is a subclass of `threading.Thread`, running as a daemon (`self.daemon = True`) in a separate `while` loop.
   - Every 2 seconds (configurable), it queries Redis for due tasks (`get_due_aggregation_tasks`).
   - For each due task, it runs the full aggregation flow: fetches the policy, fetches the accumulated data, calls `calculate_aggregated_data()` on the strategy, publishes the result via MQTT, and re-schedules the task in the queue.

This ensures that computing the average of 10,000 data points never blocks the Gateway from ingesting new data from other devices.

### Policy Specification Protocol

To enable efficient communication between the CMM and the Gateway, the framework uses a lightweight, deterministic serialization protocol. The syntax follows the format: `ACTION[:PARAMETERS[:WINDOW]]`.

| Privacy Scenario | Serialized `policy_key` | Gateway Behavior |
|---|---|---|
| Total Blockade | `BLOCK` | Silently drops the data packet. |
| Transparency (Raw) | `RAW` | Forwards original data without any modification. |
| Location Obfuscation | `NOISE:sigma=50` | Applies Local Differential Privacy (Gaussian noise, σ=50). |
| Temporal Minimization | `AVG::60` | Buffers packets for 60s, then transmits only the arithmetic mean. |
| PII Masking | `MASK:visible_chars=2` | Masks PII string fields, keeping only the first N characters visible. |

A parsing factory dynamically instantiates the required strategy class based on the `ACTION` string at runtime.

### Detailed Data Flows

#### Flow A: Real-Time Data (e.g., `RAW` policy)

1. Device publishes to topic `devices/1/data`.
2. Gateway (`on_message`) receives the packet.
3. `_get_or_fetch_policy` looks up the policy in `CacheManager`.
   - **Cache Miss:** `CMMAPI.get_privacy_policy()` is called, the CMM API is queried, and the result is saved in Redis by `CacheManager.set_policy()`.
   - **Cache Hit:** `CacheManager.get_policy()` returns the cached JSON policy.
4. `_apply_policy` is called with the resolved policy.
5. `parse_policy_key` parses the `policy_key` string.
6. `get_treatment_strategy("RAW")` returns a `RawStrategy` instance.
7. `RawStrategy.execute()` is called and returns the original payload.
8. Since `execute()` returned data, the Gateway publishes it to topic `processed_data/1`.

#### Flow B: Aggregated Data (e.g., `AVG::60` policy)

**Step 1 — Data Ingestion (Main Thread):**

1. Device publishes to `devices/1/data`.
2. `handle_received_data` → `_get_or_fetch_policy` (fetches/caches the `AVG` policy).
3. *(On first call)* `_kickstart_aggregation_task` detects an `AVG` policy, calculates `now + 60 seconds`, and calls `cache_manager.schedule_aggregation_task()`, adding the task to the Redis Sorted Set.
4. `_apply_policy` → `get_treatment_strategy("AVG")` → `AverageStrategy.execute()` is called.
5. `AverageStrategy` calls `cache_manager.add_data_point()` to save the data point to the Redis List.
6. `AverageStrategy.execute()` returns `None`.
7. The Gateway sees `None` and **publishes nothing**. The ingestion flow ends here.

**Step 2 — Average Computation (Scheduler Thread):**

1. *(60 seconds later)* `Scheduler.run()` wakes up.
2. `cache_manager.get_due_aggregation_tasks()` queries Redis (`ZRANGEBYSCORE`) and finds task `1:1`.
3. `_process_aggregation_task` is called.
4. `cache_manager.get_and_clear_data_points()` atomically fetches and clears the data list.
5. `get_treatment_strategy("AVG")` is called.
6. `AverageStrategy.calculate_aggregated_data()` computes and returns the mean.
7. The Scheduler publishes the result to topic `processed_data/1/avg`.
8. `_reschedule_aggregation_task` re-adds the task to the Redis Sorted Set for the next cycle.

### Setup and Execution

1. **Environment Variables:** Create a `.env` file at the project root with the following variables:
   - `MQTT_HOST`, `MQTT_PORT` — MQTT broker address.
   - `CMM_API_URL` — Base URL of the CMM REST API.
   - `CMM_NOTIFICATIONS_TOPIC` — e.g., `policies/updates`.
   - `DEVICE_DATA_TOPIC` — e.g., `devices/+/data`.
   - `PROCESSED_DATA_TOPIC` — e.g., `processed_data`.
   - `CACHE_TTL_SECONDS` — e.g., `900`.
   - `AGGREGATION_QUEUE_KEY` — e.g., `tasks:aggregation_due`.
2. **Installation:** `uv pip install -r requirements.txt`
3. **Dependency Services:** Ensure the **CMM**, a **Redis** instance, and an **MQTT Broker** are running before starting the Gateway.
4. **Run:** Execute `python main.py` to start the Privacy Gateway.

### Visão Geral

O Gateway de Privacidade (GP) é o componente de execução (*enforcement*) do arcabouço de software. Ele atua como um *firewall* de privacidade, posicionando-se entre os dispositivos IoT e os serviços de backend do ecossistema.

Sua responsabilidade primária é interceptar 100% dos dados brutos gerados pelos dispositivos e aplicar as políticas de privacidade e consentimento em tempo real, antes que esses dados sejam encaminhados para qualquer outro serviço.

O GP foi projetado para ser:

- **Reativo:** Responde instantaneamente a mudanças de consentimento (revogações, concessões) publicadas pelo Módulo de Gerenciamento de Consentimento (MGC).
- **Performático:** Utiliza um cache de alta velocidade (Redis) para tomar decisões de privacidade com latência quase nula, sem a necessidade de consultar o MGC a cada dado recebido.
- **Com Estado (*Stateful*):** É capaz de executar políticas de privacidade complexas e temporais, como agregação de dados (ex: "enviar média a cada 10 minutos").
- **Extensível:** Construído sobre o *Strategy Pattern*, permitindo que novos tratamentos de dados (anonimização, ofuscação, etc.) sejam adicionados sem alterar a lógica central do gateway.

### Padrões de Projeto e Lógica Central

A funcionalidade do GP é baseada em três padrões de projeto principais que trabalham em conjunto.

#### a. Strategy Pattern (Padrão de Estratégia)

Esta é a espinha dorsal da lógica de tratamento de dados. Em vez de um `if/elif/else` monolítico no gateway, nós delegamos a responsabilidade do *como* fazer um tratamento para classes de estratégia específicas.

1. **Interface Base (`TreatmentStrategy`):** Define um contrato comum com um método `execute()`.
2. **Interface de Acumulação (`AccumulatedStrategy`):** Uma especialização que herda da base e adiciona um contrato `calculate_aggregated_data()`, separando a lógica de ingestão da lógica de cálculo.
3. **Estratégias Concretas (`RawStrategy`, `AverageStrategy`):**
   - `RawStrategy.execute()`: Simplesmente retorna o payload original.
   - `AverageStrategy.execute()`: Adiciona o dado ao Redis e retorna `None`.
   - `AverageStrategy.calculate_aggregated_data()`: Recebe uma lista de dados do Redis e retorna a média.
4. **Fábrica (`treatments.factory`):** O `Scheduler` e o `Gateway` usam a fábrica (`get_treatment_strategy()`) para obter a instância da estratégia correta com base na `chave_politica`, sem nunca precisarem saber os detalhes da implementação.

#### b. Gerenciamento de Estado com Redis (`CacheManager`)

O `core/cache_manager.py` é o único módulo que "sabe falar" com o Redis. Ele gerencia três tipos distintos de dados:

1. **Políticas (Cache de Curto Prazo):**
   - **Chave:** `policy:{titular_id}:{dispositivo_id}` | **Tipo:** `String` (JSON) | Armazenado com `SETEX` (TTL automático), invalidado pela notificação "push" do MGC.
2. **Dados Acumulados (Buffer Temporal):**
   - **Chave:** `data:{titular_id}:{dispositivo_id}` | **Tipo:** `List` | `AverageStrategy` usa `LPUSH` para adicionar dados. O `Scheduler` usa `LRANGE` e `DEL` para consumir a lista atomicamente.
3. **Fila de Tarefas (Agendamento):**
   - **Chave:** `tasks:aggregation_due` | **Tipo:** `Sorted Set` | O `Scheduler` agenda tarefas com `ZADD`, usando o `timestamp` de execução como "score". Ele consome a fila usando `ZRANGEBYSCORE(0, now)`.

#### c. Processamento Assíncrono (Scheduler)

O GP opera em duas *threads* principais para evitar bloqueios:

1. **Thread Principal (Ingestão de Dados):** O `mqtt_client.loop_forever()` é bloqueante e roda no *foreground*. Sua única função é receber mensagens o mais rápido possível e delegá-las.
2. **Thread do Scheduler (Processamento Temporal):** O `Scheduler` é uma subclasse de `threading.Thread`. Ele roda em *background* (`self.daemon = True`) em um loop `while` separado.
   - A cada 2 segundos, ele consulta o Redis por tarefas vencidas (`get_due_aggregation_tasks`).
   - Se encontrar tarefas, executa a lógica de agregação completa: busca a política, busca os dados acumulados, chama a estratégia (`calculate_aggregated_data`), publica o resultado no MQTT e se reagenda na fila de tarefas.

### Fluxos de Dados Detalhados

#### Fluxo A: Dado em Tempo Real (Ex: Política `RAW`)

1. Dispositivo publica no tópico `dispositivos/1/dados`.
2. GP (`on_message`) recebe.
3. `handle_received_data` é chamado.
4. `_get_or_fetch_policy` busca a política no `CacheManager`.
   - *Cache Miss:* `MGCAPI.get_politica_privacidade()` é chamado, busca na API do MGC, e o resultado é salvo no Redis pelo `CacheManager.set_policy()`.
   - *Cache Hit:* `CacheManager.get_policy()` retorna o JSON da política.
5. `_apply_policy` é chamado com a política.
6. `parse_policy_key` traduz a `chave_politica`.
7. `get_treatment_strategy("RAW")` retorna uma instância de `RawStrategy`.
8. `RawStrategy.execute()` é chamado e retorna o payload original.
9. Como o `execute()` retornou dados, o GP os publica no tópico `dados_processados/1`.

#### Fluxo B: Dado Agregado (Ex: Política `AVG::60`)

**Etapa 1 — Ingestão do Dado (Thread Principal):**

1. Dispositivo publica no tópico `dispositivos/1/dados`.
2. `handle_received_data` → `_get_or_fetch_policy` (Busca/salva a política `AVG`).
3. *(Na 1ª vez)* `_kickstart_aggregation_task` é chamado. Ele vê que a política é `AVG`, calcula `agora + 60 segundos` e chama `cache_manager.schedule_aggregation_task()`, adicionando a tarefa à fila do Redis.
4. `_apply_policy` → `get_treatment_strategy("AVG")` → `AverageStrategy.execute()` é chamado.
5. `AverageStrategy` chama `cache_manager.add_data_point()` para salvar o dado na lista do Redis.
6. `AverageStrategy.execute()` retorna `None`.
7. O GP vê `None` e **não publica nada**. O fluxo de ingestão termina aqui.

**Etapa 2 — Processamento da Média (Thread do Scheduler):**

1. *(60 segundos depois)* A `Scheduler.run()` acorda.
2. `cache_manager.get_due_aggregation_tasks()` consulta o Redis (`ZRANGEBYSCORE`) e encontra a tarefa `1:1`.
3. `_process_aggregation_task` é chamado.
4. `cache_manager.get_and_clear_data_points()` busca a lista de dados e a apaga.
5. `get_treatment_strategy("AVG")` é chamado.
6. `AverageStrategy.calculate_aggregated_data()` é chamado com a lista de dados, calcula a média e a retorna.
7. O Scheduler publica o resultado (a média) no tópico `dados_processados/1/avg`.
8. `_reschedule_aggregation_task` é chamado. Ele lê o intervalo da política, calcula `agora + 60 segundos` e coloca a tarefa de volta na fila para o próximo ciclo.

### Configuração e Execução

1. **Variáveis de Ambiente:** Crie um arquivo `.env` na raiz do projeto com as seguintes variáveis:
   - `MQTT_HOST`, `MQTT_PORT` (do broker MQTT)
